# Lessons

- When recognizing external agent or tool processes inside tmux panes, prefer matching configured fragments against the pane process and descendant process commands. Avoid relying only on `pane_current_command`, because wrappers can expose misleading names like Node versions or architecture-specific launcher names.
- Do not turn a reversible retention-policy choice into an upfront architecture gate. Separate durable facts from transient work state, preserve both options in the design, and defer deletion timing until there is an operational need or measured storage evidence.
- For a daemon change, source tests and review are not the delivery boundary. If the request is to make the running service work, completion requires building the deployable artifact, installing it through the documented workflow, restarting the daemon, and exercising the live ingress-to-handler path.
- When a public optional value has an associated update timestamp, model and test them as one presence-aware pair. Define preserve, set, clear, and fallback-selection semantics explicitly, including the exact downstream copy for the both-absent case.
- Do not assign destructive meaning to an empty legacy proto3 scalar when absence and empty are wire-indistinguishable. Reserve clear semantics for a presence-aware field and treat legacy empty input as no change.
- When one acquisition sample can produce independent facts, model each fact as optional and persist any useful subset. Do not require one classifier to succeed before recording another valid observation from the same sample.
- Treat every type that temporarily carries raw process or screen text as a privacy boundary: omit or manually redact `Debug`, strip complete terminal control strings including C1 forms, and test that sentinel secrets cannot escape diagnostics.
- Reserve sentinel identifiers against user configuration, and make ambiguous identity resolution typed before logging or projection so a configured provider cannot collide with the unknown identity.
- Treat an accepted slice as an integration gate, not as overall completion. Before reporting completion, reconcile the latest authorization against every unchecked task in the approved implementation plan and continue while any authorized work remains.
- Reconcile summary precedence by semantic recency, not by source class alone: a substantive prompt visible while Busy is the current instruction and must replace a retained completed summary; an Idle placeholder must be rejected while the most recent substantive completed summary remains available.
- Do not substitute fake-port or disposable-process verification for an explicitly required real-provider acceptance gate. Record each real provider, concurrency combination, dashboard transition, and external blocker separately so partial live evidence cannot be reported as a full pass.
- An ingress filter does not repair already-durable invalid candidates. When a newly forbidden value may exist in event history or current projections, add a durable reconciliation transition that invalidates the historical candidate and prove restart replay keeps it cleared without matching legitimate containing text.
- When a coordinator owns an isolated live process, resolve its tmux pane, current command, exact configuration, store, and launch command before replacing it. Reuse that launch surface for replay acceptance; a different local configuration is not equivalent evidence even when it binds the same port.
- Do not assume a meaningful submitted prompt remains adjacent to the composer or inside the visible tmux grid. Keep frequent state capture small, but let a provider-specific recovery adapter search a configurable styled scrollback tail on bounded recovery triggers; distinguish submitted history from the composer before selecting text.
- Do not assign retained tmux scrollback to a replacement process merely because the pane has a new incarnation identity. Baseline the recognised prompt sequence for each incarnation and require later ordered overlap before treating a prompt as newly observed work.
- A runnable application should expose a normal binary target early enough that the documented default command works. An example-only demo is useful for visual feedback, but it must be clearly labeled and must not be mistaken for the final `cargo run` experience.
- Cargo accepts one positional test filter per `cargo test` invocation. When a verification step names distinct module suites, list separate commands rather than a plausible-looking multi-filter command that Cargo will reject.
- Derive an agent work summary from the most recent substantive submitted user instruction, not the current input composer. Adapters may scan several recent user turns to skip empty, system, tool-result, and UI-placeholder entries, but must not synthesize or concatenate them unless explicitly requested.
- Do not make an exploratory live demo wait for the final completion-review gate once its focused tests and build are green. Launch it in the assigned test pane so the user can evaluate the interface while independent review continues; reserve the gate for completion claims and integration.
- Do not measure a per-frame TUI layout by rendering a cloned paragraph into a worst-case synthetic screen. Derive the fit decision directly from bounded input graphemes and wrapping rules so draw cost is proportional to content, not a large artificial terminal area.
- During a persistent coordination task, answer status or pane-identification questions without yielding the workflow. Resume monitoring and dispatch immediately in the same turn unless the user explicitly asks to pause or changes the objective.
- End-to-end screen testing for an agent dashboard must exercise real configured agent processes, not only the dashboard process. Start each supported agent in isolated tmux panes, submit controlled work, observe busy and idle transitions plus work-summary accuracy through the real backend stream, navigate to each pane, and record pane/process identities and captures.
- For a new operator-facing TUI, prioritize an early visible vertical slice in the designated adjacent worker pane. Establish only the minimum domain/text foundation needed, then render representative data, exercise it with Ratatui `TestBackend`, and leave a live demo available for visual feedback before completing non-visual infrastructure.
- For a per-frame detail panel, avoiding a synthetic render buffer is not enough if the same owned line model is constructed twice. Build one lifetime-generic line vector, borrow it for measurement, then move it into rendering; test that long-lived agent strings remain borrowed.
- For late-joining or reconnecting consumers, store the current projection and its source event-stream revision in application state. Seed live subscriptions from that projection and use monotonically increasing revisions so snapshot delivery and subsequent updates cannot leave a gap.
- In a shared dirty worktree, do not stash, move, or hide another worker's partial changes to manufacture a clean verification surface. Keep them visible, make the requested edit surgically, and report which checkout-wide gates are blocked by the preserved concurrent slice.
- In an operator dashboard, prioritize the operator's next decision over implementation provenance. Show a concise description of what an agent is working on; keep hook-versus-screen evidence available to diagnostics rather than spending primary table or detail-panel space on it.
- In the Harold workspace, distinguish the durable `EventStream` domain log from the similarly named transient `StreamEvent` progress message. Evaluate new domain facts for the durable stream first; use live channels to distribute projections, not as substitutes for recording those facts.
- Keep one append-only screen-testing ledger that separates live terminal/browser evidence from deterministic buffer tests and from work not yet run. Record exact commands, targets, dimensions, observable results, and evidence limitations while the context is fresh.
- Keep the coordinator pane focused on orchestration: assign implementation to bounded workers, reconcile their shared-worktree changes, direct live testing in the designated test pane, and reserve coordinator edits for plans, lessons, and evidence ledgers.
- Keep the dashboard coding agent and live TUI test surface in their explicitly assigned panes. For this workspace, `%23` is the coding agent and `%26` is the live TUI test/demo pane; do not run the demo over the agent UI.
- Match reconnection semantics to the consumer's need: current-state consumers should receive a fresh projection first; event-oriented consumers may later resume from a durable event cursor. Do not build cursor replay into a state-only MVP.
- Search over a live inventory should filter the client's current authoritative snapshot unless server-side scale or pagination proves a query API is necessary. Keep streaming updates active while filtering and preserve selection by stable incarnation identity.
- Terminal wrapping must be measured in grapheme clusters and display cells, not Unicode scalar values. Reuse Ratatui's public `styled_graphemes` boundary and cell-width behavior, and add CJK odd-width plus ZWJ and combining-cluster regressions before claiming wrapped detail cannot clip.
- Tmux server reachability is not proof that the current process was invoked inside tmux: an outside process may still query an attached client. Before capturing or switching a client, require the invoking process's own non-empty `TMUX` and `TMUX_PANE` context through a testable environment boundary, and keep raw command stdout/stderr out of public `Debug` surfaces.
- Treat `q` as the dashboard's sole normal quit key. In search editing, `Esc` always clears the query and exits editing, including when the query is already empty; outside editing, it clears an accepted filter and is a no-op only when no filter exists. Verify all paths with state tests and live `tmux send-keys` evidence.
- Treat provider prompt placeholders and input affordances as UI chrome, never as work summaries. Exclude configured idle placeholders during extraction, continue scanning for the submitted task, and preserve the last genuine summary across the busy-to-idle transition.
- Unit tests for key-state transitions and a fake tmux command runner do not prove live keyboard navigation. For a tmux TUI, drive the designated test pane with `tmux send-keys`, inspect the rendered selection/search changes, and prove Enter switches only the invoking client before calling navigation complete.
- When `Esc` already cancels an editing mode, do not overload it as the application's normal quit key. Keep one explicit quit key, verify `Esc` both inside and outside the mode, and update runtime handling, demos, terminal hints, and operator documentation together.
- When a feature is expected to become part of an existing service, do not optimize prematurely for standalone isolation. Keep the service coupling intentional by naming each input port, state reducer, projection, subscription, and effect boundary so later integration does not become implicit shared-state plumbing.
- When an interaction contract changes after implementation has begun, search the entire retained plan and evidence corpus for superseded behavior, not only user-facing docs and current tests. Historical RED/GREEN evidence may stay, but prescriptive plan text must describe the final contract.
- When designing agent-state detection, do not treat lifecycle hooks and screen inspection as mutually exclusive. Use explicit hooks as the primary signal, then use provider-specific markers from the currently visible pane as a corroborating or recovery signal, with provenance and conflict rules made explicit.
- When discussing facilities found in a workspace dependency, explicitly separate APIs that exist in source from components the application actually instantiates. Do not describe dormant library behavior as current application behavior.
- When restarting a raw-mode TUI through `tmux send-keys`, do not assume the quit key was consumed before the shell is ready. Send quit, wait until `pane_current_command` is the expected shell and the prompt is clear, then send the launch command and Enter separately; otherwise a late quit character can prefix the shell command.
- When the active pane is designated as the coordinator, do not also count it as an implementation worker merely because its current directory matches one workstream. Keep coordination isolated and launch or assign distinct worker panes before claiming both tracks are active.
- When the user has asked for persistent coordination until an outcome is done, a status or time-estimate reply is not a stopping point. Keep the coordinator turn active: reconcile worker panes, route review findings, advance the next gate, and monitor until completion or a genuine user-dependent blocker.
- A compensating supervisor proves that an installed daemon can run, not that the documented background deployment recipe restarted it. For deployment acceptance, remove the compensating owner, run the recipe from a durable caller, attribute the listener PID to the recipe's exact command and ancestry, remove the caller, and prove the same PID remains listening.
- Resolve relative Markdown links from the directory containing the linking document after files move. A repository-root-looking target inside a nested README needs the appropriate `../` prefix, and the final path must be checked on disk.
